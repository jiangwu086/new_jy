# 新就业形态劳动者安全警示服务 - 系统架构方案

## 关于 DDD (领域驱动设计) 的思考
你提到的非常对，对于第一期（主要针对35万骑手，核心业务是“线下打卡+核销”）来说，**严格的 DDD（领域驱动设计）确实太重了**，会导致过度设计、增加开发成本和理解门槛。
**推荐方案：模块化单体架构 (Modular Monolith) + 经典三层架构 (MVC)**
*   **按业务分包 (Package-by-Feature)**：不要按 `controller/service/mapper` 这样纯技术分包，而是按业务分包，例如 `checkin` (打卡模块), `location` (点位模块), `user` (用户模块)。
*   **好处**：目前开发极快，心智负担低。且因为代码已经按业务模块聚拢，当三期（150万+用户，加入更多活动）并发量飙升时，可以非常轻松地把 `checkin` 模块直接拆分成独立的微服务。

## 1. UI / UE / UX 设计规范
*   **UI (视觉交互)**：
    *   **色彩体系**：主色调使用 **安全蓝 (#3B82F6)** 搭配 **纯净白**，辅以 **警示橙 (#F59E0B)**。符合政务公益项目的严肃性，同时具有警示意味。
    *   **高信息密度**：字号适中偏大（户外强光下易读），去除一切非必要的边框和装饰线条，采用卡片式设计。
*   **UE (用户体验)**：
    *   **极速原则**：主路径（扫码 -> 确认身份 -> 拍照 -> 成功）必须在线性流畅，**确保1分钟内完成**。
    *   **无感绑定**：首次使用不需要繁琐的注册流程，扫码后结合微信静默授权自动完成注册。
*   **UX (风险控制)**：
    *   **零互动**：前端彻底不设“评论、发帖、分享奖励”等功能，杜绝舆情风险。
    *   **强视觉反馈**：积分增加、达到打卡上限等关键节点使用大图标、高亮文字。

## 2. 页面规划与详细交互流程

### 2.1 骑手端 (微信小程序原生)

**1. 首页 (Home Page)**
*   **功能定位**：小程序的默认启动页，核心导航中枢。
*   **页面元素**：
    *   **顶部区域**：搜索栏/地址栏（显示当前所处区划，如“历下区”）。
    *   **Banner区**：轮播图，展示活动公告、政策宣传海报。
    *   **金刚区 (四大金刚)**：四大入口图标（扫码打卡、教育点导航、我的记录、积分兑换）。
    *   **公告跑马灯**：滚动展示政府发布的最新安全警示或活动通知。
    *   **附近推荐卡片**：基于当前GPS坐标，推荐距离最近的2-3个教育点位及其状态（营业中/休息中）。
    *   **底部 Tab Bar**：首页、导航、记录、我的。
*   **交互与数据流**：
    *   **冷启动拦截**：进入首页时，隐式调用 `wx.login` 获取 code，与后端交换 `openid` 并颁发自定义 JWT Token。紧接着弹窗请求用户的 `scope.userLocation` (GPS位置权限)，若拒绝，则附近点位仅根据IP或默认区划显示。
    *   **扫码触发**：点击中心最大的“扫码打卡”按钮，调起原生扫一扫（`wx.scanCode`）。
        *   **分支判断**：解析二维码包含的点位ID。若点位已下线，弹窗阻断“该教育点暂未开放”；若点位正常，携参数跳转至【打卡信息核验页】。
    *   **刷新机制**：页面支持下拉刷新（`onPullDownRefresh`），重新获取附近点位及个人状态。

**2. 扫码打卡核心链路 (Check-in Flow)**
这是系统最核心的履约路径，设计必须确保线性、流畅、无歧义，且极速完成。
*   **步骤一：信息核验页 (Check-in Form)**
    *   **页面元素**：顶部展示当前扫码匹配的点位名称与区划；表单包含“身份证号”及“手机号”输入框；底部“下一步：现场拍照”按钮。
    *   **交互与数据流**：
        *   **首次验证**：若用户是首次打卡，输入框为空。用户需手工输入18位身份证号；手机号输入框点击时，唤起微信原生获取手机号组件（快速验证手机号归属）。系统仅作格式校验，不强制实名公安库比对以降低门槛。
        *   **老用户回显**：若后端通过 `openid` 识别为老用户，身份证和手机号以脱敏形式（如 `138****5678`）只读回显，不可随意更改，防止一机多刷。
        *   **逻辑拦截**：点击“下一步”时，后端接口预校验。若该用户当前计费周期（如本月）的打卡次数已达上限，直接拦截弹窗：“本月有效打卡次数已满，感谢您的参与！”，流程终止。若未满，则获取 `scope.camera` 权限进入拍照页。

*   **步骤二：现场拍照页 (Check-in Photo)**
    *   **页面元素**：全屏相机实时画面；中间叠加一层浅色人形虚线轮廓，引导用户与工作人员同框；画面左下角实时渲染当前时间戳及高精度 GPS 坐标水印；底部为圆形快门按钮。
    *   **交互与数据流**：
        *   **严格限制**：仅可使用系统 `<camera>` 组件实时拍摄，绝对屏蔽 `wx.chooseImage` (禁用相册选图)。
        *   **GPS防刷校验**：点击拍摄瞬间，小程序获取当前精准经纬度，与预置的该点位经纬度计算物理直线距离。若超过允许误差（如配置阈值 200米），报错弹窗：“您当前坐标不在教育点范围内，请前往现场打卡”。
        *   **图片上云**：校验通过后，将拍摄的照片流直接上传至阿里云/腾讯云 OSS，获取唯一的 `photo_url`，同时将坐标、图片地址提交给后端 `submit` 接口。

*   **步骤三：打卡结果页 (Check-in Success)**
    *   **页面元素**：巨大醒目的成功图标（绿底白勾）；本次打卡点位名称及精确时间；积分变动高亮显示（如 `+10分`）；本期累计进度提示（如 `3 / 5 次`）；底部按钮“返回首页”及“查看记录”。
    *   **交互与数据流**：该页面屏蔽原生返回按钮，强制引导流向结束，防止产生重复提交请求。

**3. 教育点导航页 (Map & Navigation)**
*   **页面元素**：半屏地图组件 `<map>`（展示当前城市下所有可用点位的 Marker 锚点）；顶部带区划级联选择器；底部为水平滚动的点位详情卡片（包含距离、具体地址、开放时间、状态标签）。
*   **交互与数据流**：
    *   **双向联动**：滑动底部的卡片，地图上的对应 Marker 会高亮并居中；同理，点击地图上的 Marker，底部卡片会自动滚动定位到该点位信息。
    *   **唤起外导**：点击卡片上的“去这里/导航”按钮，调用 `wx.openLocation`，打开微信内置地图，并允许用户选择外部 APP（高德/百度/腾讯地图）发起真实驾车/骑行导航。

**4. 我的记录页 (My Records)**
*   **页面元素**：顶部固定数据统计栏（总可用积分、累计已消耗积分、本期已打卡次数）；下方区域为 Tab 切换列表（“打卡记录”与“积分明细”）。
*   **交互与数据流**：
    *   **列表滚动**：采用触底加载更多（分页 `limit=10`），提升大记录量下的渲染性能。
    *   **状态展示**：打卡记录中，需用不同颜色区分正常打卡（绿色）、异常打卡（红色，如被后台管理员驳回）。积分明细中，清晰标注 +（获得）与 -（线下核销）。

**5. 个人中心与信息展示页 (Profile & Info)**
*   **页面元素**：包含个人基础信息展示区；“我的兑换码”入口（出示给工作人员核销礼品）；“政策保障说明”、“工伤理赔指南”、“安全警示案例”等文章入口。
*   **交互与数据流**：
    *   点击“我的兑换码”，根据用户 `id` 和时效因子动态生成一枚刷新二维码，供线下站点工作人员扫码。
    *   点击政策与案例文章，跳转至富文本渲染页（使用类似 `mp-html` 插件解析后端返回的富文本代码），页面仅提供阅读，无点赞、评论等互动功能。

### 2.2 管理后台 (PC端 Web - Vue 3)

**1. 数据看板大屏 (Dashboard)**
*   **页面元素**：顶部四大 KPI 指标卡片（入驻用户总数、累计打卡总人次、今日打卡人数、已核销积分额）；中部核心区为 ECharts 图表（近 30 天打卡趋势折线图、不同区划覆盖占比饼图）；右侧排行榜（最热打卡点位 Top 10）。
*   **交互与数据流**：支持右上角全局时间选择器（今日、本周、本月、自定义区间），筛选条件变化时，所有卡片及图表异步发起请求联动重绘。

**2. 教育点管理 (Location Management)**
*   **页面元素**：标准后台 CRUD 列表视图（表格显示名称、区划、精确经纬度、联系人及电话、营业状态 Toggle 开关）。
*   **交互与数据流**：
    *   **点位录入**：点击新增，弹出表单。支持输入具体地址后，调用腾讯/高德 Web API 自动反解析为经纬度，管理员也可在内嵌地图组件上拖拽 Marker 进行微调确认。
    *   **物料生成**：提供“生成专属二维码”按钮，向微信服务端发起请求生成带场景值（scene=点位ID）的小程序码，支持下载单张 PNG 或批量导出压缩包，直接交由广告公司打印立牌。

**3. 打卡与用户异常审核中心 (Check-in Audit)**
*   **页面元素**：详细打卡流水表格。核心字段列包含：打卡时间、人员姓名、脱敏手机号、关联点位、现场合照缩略图、GPS 偏移距离计算结果（例如：误差 15m）、系统初判状态。
*   **交互与数据流**：
    *   **图片灯箱**：点击缩略图弹出全尺寸照片查看器，人工二次确认人员是否在现场合照。
    *   **智能预警与驳回**：系统会自动将 GPS 偏移量异常（尽管前端有拦截，但防黑客抓包破解）或照片校验失败的记录高亮标红。管理员有权限点击“作废”，作废后同步扣除骑手相应积分，并触发一次违规站内信。
    *   **台账导出**：极度重要。通过区划、周期筛选后，点击“导出 Excel”，通过流式响应下载完整数据报表，作为政府资金核销和经费下发的财务凭证。

**4. 规则与周期动态配置 (Rule Configuration)**
*   **页面元素**：表单化配置页。包括：“单次打卡获得积分额度”、“单个计费周期长度（自然月/自然季度/自然年）”、“单用户单周期最高有效打卡次数”。
*   **交互与数据流**：配置项直接对应 PostgreSQL 的 `sys_config` 表。修改保存即刻生效，不回溯历史数据，由后端的 Redis 缓存监听更新并接管最新规则。

**5. 积分核销与物资发放台账 (Redeem Management)**
*   **页面元素**：左侧为“扫码核销工作台”，右侧为“历史核销台账”列表。
*   **交互与数据流**：
    *   **核销执行**：管理员（或点位负责人）在系统后台通过输入骑手出示的兑换码（或连接扫码枪扫描），系统实时校验骑手积分余额。如果兑换需 50 积分，余额 60 分，系统提示可用；点击确认发放，扣除 50 分，记录发放点位和操作人。
    *   **防误触撤销**：提供 24 小时内的“错发撤销”功能，一键回退积分及流水。

**6. 消息推送与内容发布 (Message & Content)**
*   **页面元素**：图文文章列表（CRUD）；消息推送任务队列。
*   **交互与数据流**：
    *   **政策录入**：基于富文本编辑器（如 WangEditor）发布防暑降温、安全出行政策指引，可限定仅“槐荫区”骑手可见。
    *   **定向消息**：向筛选出的特定人群（如“最近3天内未打卡”的用户）下发微信小程序订阅消息，或对未授权消息的用户降级补发 SMS 短信。

## 3. 核心接口设计 (API)
接口设计遵循 RESTful 风格，所有 `/api/v1/*` 路由均受 JWT Token 保护。
*   `POST /api/v1/auth/login`：微信登录，获取 Token。
*   `POST /api/v1/checkin/init`：扫描线下二维码后调用，校验点位合法性及用户本期次数是否达标。
*   `POST /api/v1/upload/photo`：上传现场照片到对象存储 (OSS)。
*   `POST /api/v1/checkin/submit`：提交打卡（照片URL, 实时GPS, 点位ID）。
*   `GET /api/v1/locations/nearby`：基于用户当前经纬度，查询附近教育点。

## 4. 表结构与字段设计 (PostgreSQL)
*   `sys_user` (用户表)：`openid`, `id_card` (AES加密), `phone` (AES加密), `total_points`。
*   `edu_location` (点位表)：`name`, `longitude`, `latitude`, `status`, `district_code`。
*   `checkin_record` (打卡流水表)：**核心表**。包含 `user_id`, `location_id`, `photo_url`, `gps_longitude`, `gps_latitude`, `period` (周期标识，如 '2026-04'), `points_earned`, `status`。
    *   **关键索引**：对 `(user_id, period, status)` 建立联合索引，极速查询用户本期有效次数。
*   `points_log` (积分明细表)：记录积分增加(打卡)与减少(核销)。
*   `sys_config` (系统配置表)：键值对存储 `max_checkins_per_period` 等规则。

## 5. 非功能性架构设计
### 5.1 扩展性 (Scalability)
*   一期采用 **模块化单体 (Spring Boot)**。
*   图片文件一律存入云端 OSS，不存本地服务器，实现真正的无状态应用。
*   数据库使用 PostgreSQL，如果二期/三期扩展到全省 150 万人，PG 的表分区特性以及对 PostGIS (地理空间查询) 的天然支持，能完美抗住数据膨胀。

### 5.2 安全性 (Security)
*   **数据合规**：手机号、身份证号等 PII（个人隐私信息）在数据库中必须 AES 加密存储，后台展示时脱敏（如 `138****1234`），满足政务审计要求。
*   **防篡改**：打卡接口强制使用 HTTPS，图片水印包含隐藏的 MD5 签名。
*   **活体防刷**：小程序端严格限制只能使用 `<camera>` 实时拍摄，禁止调用相册 (`chooseImage`)，并在后端计算上传的 GPS 与点位库中 GPS 的物理直线距离（如允许误差 200 米内），异地直接阻断。

### 5.3 并发与高可用 (Concurrency)
*   **防并发“薅羊毛”**：在核心的打卡提交接口，必须使用 **Redis 分布式锁**。Key 为 `checkin:lock:{user_id}:{period}`，防止弱网环境下骑手疯狂点击按钮导致单期打卡次数超过上限。
*   **流量削峰**：打卡成功后的系统消息通知（小程序订阅消息/短信）、日志记录，通过 Spring Event 或简单消息队列异步处理，保证核心接口响应时间 < 200ms。

### 5.4 健康与可观测性 (Health & Ops)
*   引入 Spring Boot Actuator 提供 `/health` 端点。
*   针对关键业务指标（如：单日异常打卡（距离超限）次数突然飙升）设置日志告警机制。
